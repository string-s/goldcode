## 2. WebSocket 生命周期

### 2.1 总体状态流转

```text
建立 /ai 连接
  → botConnect
  → botConnected（在线大厅）
  → roundAssigned（已分配，先不要入房）
  → roundStarted（允许入房）
  → aiEnterRoom(roomId)
  → roomEntered
  → startGame
  → refreshData × N + 控制指令 × N
  → closeGame
  → matchFinished
  → roundFinished（正式赛整轮权威结果）
```

自由训练中，`matchFinished` 后进入训练状态。完成数据保存或策略更新后发送 `readyForNextMatch`，重新进入待匹配状态。

### 2.2 认证并进入大厅

WebSocket 建立后，第一条业务消息：

```json
{
  "commandType": "botConnect",
  "accessKey": "报名平台发放的AK",
  "botVersion": "my-agent-v1",
  "strategyHash": "策略文件SHA-256，可选"
}
```

成功响应示例：

```json
{
  "commandType": "botConnected",
  "botId": 12345,
  "botName": "萤火小队",
  "state": "LOBBY",
  "serverTime": 1784614800000
}
```

大厅等待时建议每 4～30 秒发送一次：

```json
{"commandType":"botHeartbeat"}
```

服务端收到任何已认证消息都会刷新连接活跃时间。客户端也应正确处理 WebSocket Ping/Pong。不要用高频心跳代替业务状态机。

### 2.3 自动分桌

系统先发送 `roundAssigned`。它只表示分配完成，不代表房间已经开放：

```json
{
  "commandType": "roundAssigned",
  "tournamentCode": "forest-2026",
  "tournamentName": "萤火森林 Agent 挑战赛",
  "roundNo": 2,
  "pairingVersion": 1,
  "assignmentType": "MATCH",
  "tableNo": 3,
  "seatNo": 1,
  "roundPoints": 0,
  "matchId": 123456,
  "matchCode": "forest-2026-r02-t03",
  "roomId": "forest-2026-r02-t03"
}
```

字段说明：

*   `assignmentType=MATCH`：正常参赛，保存 `roomId` 并等待 `roundStarted`。
    
*   `assignmentType=BYE`：本轮轮空，不会提供房间信息，也不需要入房。
    
*   `pairingVersion`：配桌版本。重开或重新配桌后，以最新版本为准。
    
*   自由训练事件还会包含 `matchType=PRACTICE`、`sessionId` 和 `batchId`。
    

系统随后发送 `roundStarted`。收到后，才在同一条 WebSocket 上发送：

```json
{"commandType":"aiEnterRoom","roomId":"forest-2026-r02-t03"}
```

正式赛入房时不要再次携带 AK。入房成功返回 `roomEntered`。如果返回：

```json
{
  "commandType": "error",
  "code": "ROOM_NOT_OPEN",
  "roomId": "forest-2026-r02-t03",
  "retryAfterMs": 2000
}
```

请保持当前连接，在 `retryAfterMs` 后重试 `aiEnterRoom`；不要重新认证，也不要切换到其他房间。

### 2.4 断线重连

断线后采用带抖动的指数退避重连，例如 1、2、4、8 秒，最大间隔建议不超过 30 秒。重连成功后重新发送 `botConnect`。服务端会补发仍有效的 `roundAssigned`；若轮次已经开始，还会补发 `roundStarted`。

客户端应以 `(tournamentCode, roundNo, pairingVersion, matchId)` 做幂等键，避免重复初始化策略或重复保存同一场比赛。收到更高的 `pairingVersion` 时，应丢弃旧房间的待执行动作。

## 3. Agent 可发送的控制指令

控制指令只允许在 `startGame` 之后、`closeGame` 之前发送。服务端会根据已认证连接自动识别精灵，当前协议不要求也不建议附带精灵 `id`。

| commandType | 作用 | data |
| --- | --- | --- |
| `goForward` | 向车头方向前进 | 不需要 |
| `goBack` | 倒车 | 不需要 |
| `turnLeft` | 向左转向 | 官方 SDK 要求必填；数值字符串 0.01～0.1（标量） |
| `turnRight` | 向右转向 | 官方 SDK 要求必填；数值字符串 0.01～0.1（标量） |
| `stop` | 停止移动 | 不需要 |
| `steerBack` | 回正方向盘/停止持续转向 | 不需要 |
| `setAttackValue` | 设置下一次碰撞使用的攻击强度 | 数值字符串；不得为负数 |

示例：

```json
{"commandType":"goForward"}
{"commandType":"turnLeft","data":"0.05"}
{"commandType":"steerBack"}
{"commandType":"setAttackValue","data":"80"}
{"commandType":"stop"}
```

实现约束：

*   精灵具有持续状态。一次 `goForward` 会持续生效，直到收到相反/停止指令或被碰撞状态暂时打断；转向同理。
    
*   转向指令的 data 不是二维向量，而是角速度大小的标量。官方 SDK 要求 turnLeft/turnRight.data 为数值字符串，范围 0.01～0.1；前端缺省值为 0.05，但参赛实现应显式传值。左右方向由 commandType 决定。实时字段 angularSpeed 也是非负大小，必须结合 dirState（-1 左转、0 直行、1 右转）判断方向。倒车时引擎会反转物理旋转符号，以保持精灵视角的左转和右转。
    
*   `setAttackValue` 设置的是期望攻击强度；实际攻击强度为“设定值与当前能量中的较小值”。例如剩余能量 30、设定 80，实际只按 30 结算并消耗 30。
    
*   实时广播数据当前不包含对手的设定攻击强度，因此策略不得假定可直接读取对手下一次攻击值。
    
*   动作指令发送频率不得高于每 100 ms 一次；相同指令仅在策略状态变化时发送。使用官方 SDK 时不得修改 100 ms 动作间隔、5 秒心跳或限频逻辑，也不得自建 WebSocket、定时器或批量/连发逻辑绕过 SDK；每次策略回调最多返回一个动作。移动和转向是持续状态，提高频率不会获得额外操作能力。
    
*   `attack`、`defend`、`removeSkill`、`addEnergy` 和 `updateConfig` 不开放给参赛 Agent。
    

## 4. 实时数据结构

### 4.1 顶层 data

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `map` | object | 仅 startGame：地图边界与障碍物，多边形集合 |
| `rabbits` | array | startGame 与 refreshData 均有：当前所有精灵状态 |
| `goldCarrot` | object/null | 仅 refreshData：森林之心坐标；无对象时为 {} 或 null |

startGame.data 与 refreshData.data 的字段并不完全相同：map 仅在开局下发，goldCarrot、elapsedSeconds 和 remainingTime 只在实时帧中出现。协议仍使用 rabbits 和 goldCarrot，业务含义分别是“参赛精灵”和“森林之心”；客户端应按字段名解析，不要根据中文展示名猜测 JSON key。

### 4.2 map

地图逻辑尺寸为 1440 × 820。map 仅随 startGame 下发一次，客户端必须缓存；当前 map 主要包含：

```json
{
  "width": 1440,
  "height": 820,
  "borders": [
    [
      [{"x":0,"y":0},{"x":120,"y":0},{"x":120,"y":820}],
      [{"x":120,"y":0},{"x":180,"y":80},{"x":120,"y":820}]
    ]
  ],
  "blocks": [
    [
      [{"x":400,"y":300},{"x":520,"y":300},{"x":520,"y":420}]
    ]
  ]
}
```

borders 和 blocks 都是三层数组，结构为 \[物体\]\[凸块\]\[顶点\]。凹形物体会被物理引擎拆成多个凸块，遍历时不能只读取 \[i\]\[0\]。顶点 {x,y} 是世界绝对坐标，可直接与精灵位置比较。碰撞与路径规划应以服务端下发的顶点坐标为准，不要把示例坐标或障碍物数量写死；精灵外形也应视为凸多边形，而不是单点。

### 4.3 rabbits\[ \]

当前实时协议中的每个精灵可包含以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 精灵/Agent 标识 |
| `name` | string | 展示名称 |
| `position` | `{x,y}` | 中心位置 |
| `velocity` | `{x,y}` | 当前速度向量 |
| `angle` | number | 朝向角 |
| `speed` | number | 移动速度 |
| `angularSpeed` | number | 转向角速度大小（标量，非二维向量） |
| `width` / `height` | number | 精灵包围尺寸 |
| `score` | number | 当前发光果实数量 |
| `energy` | number | 当前剩余能量 |
| `active` | boolean | 是否处于活动状态 |
| `moveState` | string | 移动状态 |
| `dirState` | number | 转向枚举：-1 左转、0 直行、1 右转 |
| `attacking` | boolean | 是否处于攻击/碰撞表现状态 |
| `rebounding` | boolean | 是否正在反弹 |
| `reboundAngle` | number | 反弹方向相关角度 |
| `invincible` | boolean | 是否处于森林之心增益状态 |
| `deathCount` | number | 本局淘汰次数；正常为 0 或 1 |
| `survivalTime` | number | 生存时间统计 |

示例：

```json
{
  "id": "1001",
  "name": "萤火小队",
  "position": {"x": 320.5, "y": 460.0},
  "velocity": {"x": 4.8, "y": -0.7},
  "angle": 1.42,
  "speed": 5,
  "width": 52,
  "height": 30,
  "score": 12,
  "energy": 740,
  "active": true,
  "rebounding": false,
  "invincible": false,
  "deathCount": 0
}
```

字段可能随版本增加。解析器应忽略未知字段，并为可选字段设置安全默认值。不要依赖 JSON 字段顺序。

### 4.4 goldCarrot（森林之心）

```json
{
  "x": 720,
  "y": 410
}
```

goldCarrot={} 或 goldCarrot=null 表示当前没有可拾取的森林之心；当前协议不使用 active、position、width 或 height 字段。当前游戏通常在第 30、90、150 秒附近生成，并会在生成前约 5 秒进行画面提示；以实时字段为准，不要仅依赖本地计时器。

## 5. 游戏规则与策略含义

### 5.1 初始状态与能量周期

*   每辆车初始拥有 10 个发光果实和 1000 点能量。
    
*   攻击强度由 Agent 通过 `setAttackValue` 设置，默认值为 50。
    
*   每到 30 秒周期点，仍处于活动状态的精灵能量重置为 1000，不是“在剩余值上增加 1000”。
    
*   碰撞时实际攻击强度 `actualAttack = min(configuredAttack, currentEnergy)`。
    
*   普通状态下，碰撞后消耗与实际攻击强度等量的能量。
    

因此高攻击并非总是最优：它提高单次碰撞获胜概率，但会降低周期内可持续碰撞次数。Agent 需要综合剩余能量、距下次重置时间、位置、对手状态和当前排名决策。

### 5.2 精灵对精灵碰撞

两车发生有效碰撞时：

1.  分别计算双方实际攻击强度；
    
2.  较高者获得 1 个发光果实；
    
3.  较低者失去 1 个发光果实；
    
4.  相同则双方果实不变；
    
5.  普通状态下，双方各自消耗本次实际攻击强度对应的能量；
    
6.  双方按碰撞结果进入反弹运动。
    

三个或更多精灵近乎同时相撞时，按两两碰撞依次结算，可理解为追尾/连撞。策略必须容忍同一短时间窗口内分数和能量发生多次变化。

同一精灵对或同一精灵与障碍物的连续接触存在约 1.5 秒的碰撞冷却，防止贴合时每帧重复结算。不要把“仍在接触”误判为每帧都会得分。

### 5.3 障碍物、场地边缘与淘汰

*   与障碍物发生有效碰撞：扣 1 个发光果实，并触发反弹。
    
*   连续 30 秒未与其他精灵或障碍物发生碰撞：扣 3 个发光果实；如果继续没有碰撞，将在后续周期继续扣分。
    
*   当前版本没有落水机制：精灵到达场地边缘时会被强制拉回可行驶区，不会因越界增加 deathCount，也不会触发 5 秒复活。
    
*   发光果实降至 0 时永久淘汰，本局不再复活。
    
*   场上只剩一个正分精灵时，本局可以提前结束；否则最长 180 秒结束。
    

“避战到结束”会受到无碰撞惩罚；只追求撞墙刷新活跃也会直接损失果实。Agent 应主动寻找风险可控的有效交互。

### 5.4 森林之心

精灵拾取森林之心后获得 10 秒增益，实时状态表现为 `invincible=true`：

*   与精灵碰撞时不消耗自身能量，且对未持有森林之心的精灵必胜并正常增减果实；
    
*   双方都持有森林之心时攻击强度相同，按平局处理；
    
*   撞击障碍物时不扣除果实；碰撞仍会改变运动轨迹，并非穿透或静止不动；
    
*   增益精灵撞击对手时，对手的反弹效果会更强。
    

客户端应以 `invincible` 和实时对象状态为准，不要在本地固定延长增益时间。

## 6. 碰撞与反弹计算参考

当前精灵碰撞后的核心速度计算可抽象为：

```text
vA' = 0.02 × (pA - pB) - 0.3 × vA + 0.7 × vB
vB' = 0.02 × (pB - pA) - 0.3 × vB + 0.7 × vA
```

其中：

*   `pA`、`pB`：碰撞瞬间双方中心位置向量；
    
*   `vA`、`vB`：碰撞前速度向量；
    
*   `vA'`、`vB'`：反弹初速度向量。
    

若一方速度为零，计算时会用对方运动方向的反向量进行补偿。反弹速度随后约按每帧 0.15 px 衰减；反弹结束后，精灵会恢复碰撞前的移动/转向指令状态。森林之心持有者作为撞击方时，对手反弹强度会获得约 1.5 倍系数。

这些公式用于策略模拟和风险预估，不应取代实时观测。网络延迟、多车连续碰撞、边界修正和前端离散帧都会造成预测误差。推荐每个新帧重新校正位置与速度，而不是长期纯积分推演。

### 6.1 碰撞预判建议

对于两辆车的凸多边形外形，可采用“分离轴定理（SAT）”判断当前是否相交；短期预测可将双方位置按速度外推若干帧，再用膨胀后的包围盒做快速筛选，最后用 SAT 精确判断。

建议的控制循环：

1.  解析并校验本帧；
    
2.  找到自己的精灵对象；
    
3.  更新能量重置、森林之心和无碰撞倒计时估计；
    
4.  对障碍物和所有对手做短期轨迹预测；
    
5.  评估碰撞胜率、能量成本、分数收益和场地边缘位置风险；
    
6.  只有目标控制状态变化时才发送指令；
    
7.  下一帧用真实数据纠偏。
    

## 7. 自由训练闭环

比赛结束后可在同一条已认证连接查询个人有效比赛数据：

```json
{"commandType":"getMyBattleData","limit":100}
```

`limit` 有效范围为 1～200。响应 `myBattleData` 会包含自由训练和正式赛的个人场次、对手、名次、得分、死亡次数、轮次积分和个人赛事排名；重开轮次的旧配桌版本不会作为有效结果返回。

推荐闭环：

```text
matchFinished
  → getMyBattleData
  → 保存本场实时帧、动作与结算数据
  → 离线回放/训练/更新策略
  → readyForNextMatch
  → botReady（LOBBY_READY）
  → 等待下一次 roundAssigned
```

准备好参加下一场自由训练时发送：

```json
{"commandType":"readyForNextMatch"}
```

成功响应：

```json
{
  "commandType": "botReady",
  "botId": 12345,
  "state": "LOBBY_READY",
  "serverTime": 1784614800000
}
```

重复发送 `readyForNextMatch` 是幂等的；比赛中发送会得到 `BOT_STILL_BATTLING`。也可以在训练阶段关闭连接，之后用同一 AK 重连。

## 9. 常见错误与处理

| code/现象 | 含义 | 建议处理 |
| --- | --- | --- |
| `BOT&#95;ALREADY&#95;ONLINE` | 同一 AK 已有有效连接 | 停止第二个进程；确认旧进程退出后再重连，不要无限重试 |
| `BOT&#95;CONNECT&#95;REQUIRED` | 当前连接尚未完成大厅认证 | 新连接先发送 `botConnect` |
| `BOT&#95;NOT&#95;ASSIGNED` | 正式赛尝试进入非本桌房间 | 只使用最新 `roundAssigned` 的 `roomId` |
| `ROOM&#95;NOT&#95;OPEN` | 已开轮，但该桌大屏房间尚未建立 | 保持连接，按 `retryAfterMs` 重试 `aiEnterRoom` |
| `BOT&#95;STILL&#95;BATTLING` | 比赛中提前申请下一场训练 | 等待 `matchFinished` |
| 收到重复分桌/开赛事件 | 重连补发或控制端重试 | 按配桌版本和比赛 ID 幂等处理 |
| 只收到 `closeGame` 未收到结算 | 游戏已停止，但赛事结算尚未完成 | 保持连接等待 `matchFinished` / `roundFinished` |
| 指令发送后没有效果 | 尚未 `startGame`、已 `closeGame`、精灵淘汰或命令未变化 | 检查本地状态机和最新精灵状态 |
| 无法读取对手攻击值 | 当前实时协议不广播设定攻击强度 | 通过能量变化、轨迹和历史行为做估计 |
